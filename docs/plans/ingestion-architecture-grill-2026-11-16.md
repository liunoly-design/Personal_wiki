# 三层资料摄取架构访谈

日期：2026-11-16。状态：Q1–Q15 已完成，完整规格已整理；见 [本地规格](../specs/three-layer-ingestion.md)和 [GitHub SPEC #40](https://github.com/liunoly-design/Personal_wiki/issues/40)（ready-for-agent，正文与标签已读回）。本文保留访谈依据，不是部署证明。

## 已确认的场景与边界

- 用户提供的首批场景为 X 帖子链接、抖音分享文案和微信公众号文章链接。本轮将其作为使用场景，不执行真实采集或入库。
- 第一层识别输入、来源平台及内容形态，选择第二层的处理机制；不要求先将纯文本和文件转换为网址。
- 第二层按不同来源分别获取完整内容，转换为 Markdown。微信公众号、抖音、小红书、X、普通网站、快手等逐个实现，保留持续增加来源的能力；未实测的平台不视为已支持。
- 第三层交付 Markdown、原件及来源信息给 LLM Wiki；摘要、概念、知识关联、检索和讨论由 LLM Wiki 提供。
- 视频本轮只处理语音转录，不扩展为画面理解；图文资料需要识别图片文字，保留原图、顺序和对应关系，并标明识别不确定处。
- 支持只转换、不入库；用户明确要求记录到个人 Wiki 时执行完整流程。

## 获取、待补与执行方式

- 允许自动切换获取方式，优先寻找 GitHub 上合适的库并用样本测试；必要时也可通过 Codex session 或自动化处理。具体候选库、固定版本和调用机制待核查，不因讨论而新增账户访问或费用授权。
- 未取得全文的资料存入待补区或独立文件夹，保留已取得材料和失败原因；后续解决后补齐。
- 获取失败后自动分析；日常任务最多两轮自动恢复，仍失败则进入待补，自动交接 Codex 项目开发 session 修复代码、测试，通过后沿原任务补处理。两轮上限不取消后续开发修复，修复启动不等待用户逐条指示。
- 接受用户手工补充导出文件、截图、音视频文件或粘贴正文；补充材料关联原待补任务，注明用户补充，保留已有获取记录，再继续转换和入库。
- 视频任务可发往 Mac mini，由持续运行的处理服务执行。现有服务实现和可复用接口须核对，不能把历史部署说明当作当前在线验收。
- 原件保护、重复投递去重、失败恢复、来源可追溯及既有费用/登录边界继续适用。

## 已确认的来源顺序

1. 首批用 X、抖音、微信公众号场景验收，并保留纯文字入口。
2. 随后增加普通网页链接和小红书。
3. 快手、B站、YouTube、播客、本地录音、PDF/Word 等其他来源后续逐项增加；具体后续顺序未定。

## 实施建议，尚未冻结

- CLI 承载实际执行，skill 指导 AI 调用；不同 AI 入口共用程序能力。
- 平台获取器复用正文整理、语音转录、图片文字识别和入库交接能力，避免为每个平台复制完整流水线。
- 单条待补资料恢复与通用处理器修复分别记录；修复后按原来源和任务关系补处理。
- 待补材料补齐前保留独立状态，避免将残缺正文当作全文交给 LLM Wiki 正常分析。

## 最后一轮确认

- Q14：按两轮失败进入待补执行，然后调用 Codex 项目开发 session 进行代码修复和测试。测试通过后继续补处理，维护失败仍保留材料和诊断。
- Q15：选择 A。未接入平台先尝试已有通用方式，失败登记待补；新平台按确定的顺序逐项接入，不自动开发。

本轮无待补充的产品访谈问题；候选库、调度桥接和真实服务能力归工程核查，具体方案及验收见完整规格。
