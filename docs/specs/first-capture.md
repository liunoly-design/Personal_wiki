# 首版：收集文本、X 与微信公众号并构建可追溯 Wiki

状态：用户已确认 Q1–Q24 及测试入口，并授权基于 nashsu 安装落地、使用先前提供的 X 和微信链接实测。规格已发布为 [Issue #1](https://github.com/liunoly-design/Personal_wiki/issues/1)。安装测试与完整规格验收分别记录，不将安装成功视为全功能交付。

## Problem Statement

用户希望在飞书发送资料后，自动保留完整原件及附件，并获得能够持续积累、关联、追溯来源的个人知识库。只保存链接或单篇摘要不能满足需求；不应重新实现已有 LLM Wiki 产品中的编译能力。

## Solution

以“小婕收集”作为入口，通过现有 OpenClaw 接收文本和平台链接。平台脚本保存原件及附件，再交给优先评估的 nashsu 底座生成 Source、Concept、实体和已有主题关联。两阶段回执说明接收、归档及加工结果。Raw 不被覆盖，人工知识受保护，综合及大范围修改进入待审清单。

## User Stories

1. 作为用户，我希望在消息开头使用收集口令，以便明确触发归档。
2. 作为用户，我希望一次发送多个链接，以便批量收集。
3. 作为用户，我希望补充个人背景且与原文分开，以便保留自己的意图。
4. 作为用户，我希望保存文本、X 和微信正文、图片及原始抓取结果，以便脱离原网站阅读和核查。
5. 作为用户，我希望 X 包含目标帖、同作者串文及引用帖，以便保留上下文，不采集其他评论。
6. 作为用户，我希望下载视频及标题简介，以便保留资料；首版不根据未转录视频生成内容摘要。
7. 作为用户，我希望超长或超大视频先提示，以便控制下载规模。
8. 作为用户，我希望收到接收与完成回执，以便知道任务进度和归档位置。
9. 作为用户，我希望 Source 包含结论、摘要、观点、事实与引用，以便快速回顾并核查。
10. 作为用户，我希望知识能提取概念和实体并关联已有主题，以便积累跨来源关系。
11. 作为用户，我希望重复链接直接返回既有资料，以便避免重复下载和加工。
12. 作为用户，我希望明确重新收集后保留变化前后的原件，以便追溯版本。
13. 作为用户，我希望临时网络失败最多尝试五次，以便自动恢复短暂故障。
14. 作为用户，我希望登录失效和验证码暂停并通知我，以便自行恢复会话。
15. 作为用户，我希望模型额度不足时保留资料并等待，以便避免未经选择的付费调用。
16. 作为用户，我希望附件失败可单独补下载，以便不重复处理成功内容。
17. 作为用户，我希望相互冲突的观点保留各自来源和日期，以便独立判断。
18. 作为用户，我希望手写及标记保留的内容不被自动覆盖，以便维护个人判断。
19. 作为用户，我希望通过编号处理待审建议，以便明确应用、跳过或稍后处理的对象。
20. 作为用户，我希望中断后原件不丢失且任务可恢复，以便长期使用本机自动归档。

## Implementation Decisions

- 优先验证 nashsu 作为主底座，接受桌面应用常驻；是否最终采用取决于外部摄入、编译和恢复验证。保留上游来源及许可证，沿用现有工程历史和开发规范。
- 平台采集与 Wiki 编译分离。已成功的单链接测试仅作为可行性证据，不能替代平台支持范围的验收。
- 首轮优先 Codex CLI 订阅登录；关闭向量搜索及付费搜索服务，不自动切换付费 API。集成兼容性尚待验证。
- Markdown 与附件为事实数据，索引可重建；Raw、Source、派生知识和个人补充说明分开，保留来源 URL、时间及哈希。
- 收集口令及别名只在消息开头匹配。重复链接返回已有归档；显式重新收集时重新抓取，变化内容另存版本。
- 视频最高 1080p，不自动展开播放列表。超过 30 分钟或预计 1 GB 需确认继续；未知大小达到 1 GB 暂停。
- 临时网络错误最多五次尝试，含首次。登录/验证码及模型额度不足分别进入等待处理状态；正文成功但附件失败为部分完成。
- 原件保护、重复投递和并发写入必须由程序保障。中断恢复、原子提交和消息幂等的具体实现根据上游实际能力确定。
- 自动生成来源卡、概念/实体及已有主题关联；综合文章和大范围重构待审。冲突保留双方证据，人工内容不可自动覆盖，无法区分时待审。
- 待审清单持久保存，每项有编号；回执携带本次新增事项，支持应用、跳过、稍后。首版不新增定时提醒。

## Testing Decisions

建议以提交收集消息为统一业务测试入口，观察归档文件、引用、任务结果及回执。平台网络和模型调用可替换为确定性样本，以便可重复验证失败行为；另做少量真实抓取及模型集成验证。当前仓库已有抓取实测记录，尚无正式工程测试框架。

| 场景 | 可观察验收结果 |
|---|---|
| 文本、X、微信成功收集 | Raw、附件与 Source 可定位，回执包含标题、摘要、位置和附件状态 |
| 概念及关联生成 | 派生知识引用可解析，能追溯 Source 与 Raw |
| 重复消息或链接 | 不重复归档、不重复加工，返回已有结果 |
| 显式重新收集且内容变化 | 新旧原件均保留，旧哈希不变 |
| 网络连续失败 | 总尝试不超过五次，达到上限后明确报告失败 |
| 登录、验证码、额度限制 | 进入对应等待状态，不盲目重试或自动付费 |
| 附件失败 | 部分完成，可仅补失败附件 |
| 视频阈值 | 超限等待确认，未知大小达到上限暂停 |
| 新旧观点冲突 | 来源和日期并列，未静默删除旧结论 |
| 人工内容或归属不明 | 保护人工内容；不能安全更新则生成待审建议 |
| 待审编号操作 | 仅影响指定事项，已有历史与来源保留 |
| 编译崩溃或应用重启 | 原件哈希不变，任务可恢复，不伪报完成 |
| 应用窗口关闭或切换项目 | 验证实际处理行为；不能运行时明确等待，不丢任务 |

## Out of Scope

- 当前交付不处理抖音；YouTube、其他博客不作为本次验收前提。
- 视频转录、录音、文档导入、定期知识 Review、GTD 行动交接属于后续范围。
- 首版不自动发布综合文章或执行大范围重构，不购买外部服务。
- 不修改 Apple 任务；当前规格不授权部署、读取私人账户或发送测试外部消息。

## Further Notes

真实 Vault 已确定且独立于代码仓库。原型优先使用合成内容及已授权的公开样本，凭据和真实附件不进入 Git。备份、同步及真实登录会话的运行安排在正式使用前另行确定。上游无法满足关键行为时，记录具体缺口后决定适配或更换底座，不能将文档支持等同实测通过。
