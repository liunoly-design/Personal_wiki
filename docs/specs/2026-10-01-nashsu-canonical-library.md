# 以 nashsu 为统一资料入口

状态：用户已确认推荐写入方式、阅读形式、任务恢复与清理，并授权开发。规格 Issue #14；实现任务 #15–#17；目标版本 0.4.0；本机交付 0.4.0-preview.2。

## 用户已确认的方向

- 使用 nashsu 查看正式资料、理解处理结果，后续查询与阅读优先通过 nashsu API。
- 尽量采用 nashsu 原生功能和目录，避免额外阅读库与多个流程重复操作同一篇文档。
- Agent 中间产物放内部工作区，确认正式内容成功写入后可删除；不在用户资料列表长期保留。
- 概念解释等结果写入指定的正式知识文件。
- 既有原件保护、来源可追溯要求继续有效。

## 已核对事实

- nashsu 初始化自带 raw/sources、raw/assets 和 wiki 下的标准知识分类。上次回复把 raw/assets 本身说成自建目录不准确；按来源 ID 组织归档是集成层的安排。
- 公开文件读取 API 允许 wiki/**、raw/sources/** 及 purpose.md/schema.md，不包含根目录 reading/**、raw/inputs/** 或隐藏工作目录。
- 当前处理代码仍依赖 .personal-wiki 中的生成请求、结果记录、分段翻译缓存和待审提案。不能在未修改恢复/去重逻辑前整体删除。

## 已确认的阅读与任务流程

- 每篇文章以 wiki/sources 下的一页为主要阅读入口，含完整中文正文、简短资料说明与原文链接；概念/实体独立关联。原文保留在 raw/sources，附件保留在 raw/assets。
- 取消独立 reading 与 raw/inputs 的用户可见入口；迁移引用后去除冗余副本，collected 不再因绕开原生流程而额外保留。
- 临时数据迁至 Vault 外的 Agent 工作区。成功写入后核对全文、附件、链接和 API 可读性，持久化最小完成凭据后清理可重建缓存。
- 失败阶段保留恢复数据；待审提案在决策前保留。来源 ID、去重及校验记录不与全文缓存混为一谈。
- 一个明确的写入流程负责最终知识文件；采用原生编译前验证手写内容保护与失败恢复，不同时启动两套编译。

## 启动恢复和清理的验收规则

1. 收到任务先持久化，再确认收到并开始下载；任务与来源分别使用稳定 ID。
2. 记录下载、翻译、知识提取、概念整理、正式发布、API 核验、清理等阶段的结果。重启只补未完成阶段。
3. 成功必须包括完整中文阅读页、来源证据、必需附件和知识结果；翻译待处理、缺附件或写入未核验均不得视为可清理。
4. nashsu API 读回正式正文并核对预期内容，原件和附件执行本地完整性校验。API 不支持直接读取 raw/assets，因此不伪称附件已由该 API 验证。
5. 先持久化最小完成凭据，再清理临时文件，最后从活动任务列表移除。凭据仅保留去重、来源关联、结果定位和核验信息；不保留重复全文缓存。
6. 清理中断可重入；正式内容已提交但尚未记录完成时，先核验现有结果，不重新调用模型、不重复生成知识。
7. 启动扫描全部活动任务和工作区。根据已持久化结果恢复 queued/processing/retry/publishing/verifying/cleanup_pending。历史 failed 和“done 但翻译或附件不完整”的任务也要重新判定。
8. 无任务记录但残留工作区的，依据可信元数据恢复关联；无法关联的保留待检查，不盲删，不猜测来源。
9. 网络错误按既定有界重试与退避处理；登录、验证码、额度不足保留等待原因，恢复条件满足后续跑，不无限循环、不切换付费服务。
10. 同一任务只有一个有效执行者；并发启动、重复消息、进程中断不能造成重复处理或提前删除。
11. 既有手写内容及待审修改不因清理丢失；待审状态可见，不将未应用候选伪报为已写入。
12. 启动恢复先完成目录检查，再接收新任务；长任务不阻塞其他可处理任务。每个任务的等待原因和完成状态可查询。

## 开发拆分草案

1. **统一正式阅读页与 API 核验**（无前置）：以一个新任务验证原文、完整中文页、概念关联都落在 nashsu 原生目录，原生 API 可读、可搜索；不再产出 reading/inputs/collected 的重复正式副本。
2. **持久任务恢复与成功后清理**（依赖 1）：覆盖任意阶段中断后重启、失败等待、重复投递、核验失败不删除、清理中断再入、最小完成凭据。
3. **历史任务及目录迁移与上线**（依赖 1、2）：盘点旧结果和引用，先备份、迁移及核验，再清理已确认冗余的临时产物；重启真实服务检查自动恢复与正式资料显示。

测试沿用任务运行入口与受保护收集入口，增加本机真实 nashsu API 集成验收。验收观察最终资料、任务状态和清理结果，不测试内部函数的调用顺序。任务拆分和新增 API 测试边界已随用户“可以，推进版本”确认，发布为 GitHub #15–#17。审查基线为上一已部署版本的提交 02d011a。

## 已确认的 API 写入方式

本机 nashsu 当前 HTTP API 没有直接上传/保存正文的端点。pages/embed 是向量索引，sources/rescan 是扫描已存在文件，都不能替代正文写入。

- 推荐：一个薄的本机受保护写入层写入 nashsu 原生目录；查询、正文读取、搜索和发布核验使用原生 API。不维护平行知识库。
- 备选：扩展并维护 nashsu 桌面版的正文写入 API，再由 Agent 调用。需要额外的接口实现、鉴权、原件保护、冲突处理、构建安装及版本升级维护。

用户已确认推荐方案；不能把本机文件写入描述成 nashsu 原生 API 写入。


## 任务完成与知识待审

采集任务完成代表原文、正文与所有加工结果已可靠保存并核验。与既有页面冲突的候选单独保存为 nashsu 可见的待审文档，回执明确未覆盖原页；待审文档属于正式待审记录，不能随临时工作区清理。它不再使采集任务永久停留在执行队列。

## 真实迁移补充验收

nashsu 即使关闭自动提取，仍会在文件监控发现原始资料删除时清理关联知识页。因此迁移必须暂停文件监控并确认原生文件变更队列为空；清理旧副本后再次通过 API 核验所有发布内容，之后才能写入完成记录。正常采集仅清理 Vault 外的工作区，不删除正式原文。
